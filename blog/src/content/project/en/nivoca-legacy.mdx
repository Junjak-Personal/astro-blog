## Intro

**NiVoca** is a Japanese vocabulary app with quizzes, OCR word recognition, and other features.

I built it for my own convenience: I wanted to enter and add Japanese words more easily.  
As a Korean smartphone user, I normally use Korean/English keyboards. Adding Japanese takes me outside my usual input routine and makes it inconvenient.  
I first considered automatically changing the IME when the word input received focus. However, that capability had long been blocked because it would arbitrarily control the user’s device, so I gave up and put the idea aside for a while.

With recent AI advances making vibe-coded apps and web services so easy to build, I suddenly wondered whether I could finally create the Japanese vocabulary app I had wanted, and started developing it.

The initial need—arbitrarily switching the IME—was still impossible. When I asked AI for a design, it suggested waragana, a library that automatically converts English letters to hiragana. I considered that an acceptable compromise and proceeded.

As development continued, I wanted photo recognition for adding words and learning features with an on-device LLM using the recently released Gemma4. The result grew beyond the original plan into an app that I consider quite useful.

During development, I felt that Web / ReactNative alone limited access to native app features, especially on-device LLMs. I decided on a full Flutter refactor and to keep the Web and React Native versions as archives.

I therefore made this repository public after removing credential keys, UI design records, and a few other items.  
Because it was developed through vibe coding, I cannot guarantee the quality, but the core features are configured to work, so I hope it serves as a useful reference.

### Initial design

1. Available without signing in
2. IA organized into Words / Wordbooks / Quizzes / Settings
3. Flip between 「word only」 and 「word + meaning」 while memorizing
4. Quiz settings
  1. Initially SRS
  2. After discussion with AI about odd behavior, customize the FSRS setup (using it as-is did not fit my UI/UX)
5. Enter hiragana through alphabetic input using waragana
6. Import open-source Japanese/English word data and translate it into Korean with an LLM (claude sonnet)
7. Search the dictionary stored in the database first, then the Jisho api if missing, then an LLM (gpt5) if still absent; otherwise return no results
8. Use Supabase for database and authentication

Item 1 (guest usage) was later withdrawn.  
Initially, a separate guest store used IndexedDB (Dexie), switching Repository implementations based on login state.  
But handling migration from guest data into server data after login made state management unmanageable.  
In the end, I removed guest storage entirely and abandoned guest mode.

### Quizzes and spaced repetition

I actually spent more time here than on collecting words.

**Replacing SM-2 with FSRS**

- I first implemented the classic Anki-style algorithm (SM-2) myself, but its review intervals did not feel right.
- Switched to `ts-fsrs`, keeping default algorithm parameters and customizing only the UI/UX layer above it.
- Migration traces remain: `study_progress.ease_factor` is an SM-2-era field unused by FSRS, but the column still exists.

**Four ratings with next-interval previews**

- Four buttons: Again / Hard / Good / Easy
- Show each button’s next review time **before** it is pressed (for example, 「Easy = in 20 days」)
- Intended to avoid choosing ratings just by intuition

**Two card types**

- Word cards — flip, with word → meaning, meaning → word, or random direction
- Example cloze cards — replace the target word with `____` and offer three choices (two distractors from other words). The default ratio is 30%, adjustable in settings.

Choosing where to place the blank was trickier than expected because dictionary forms (`食べる`) appear as conjugated forms (`食べます`) in examples.

- Use the dictionary form if it appears unchanged in the sentence
- Otherwise strip trailing hiragana one character at a time to find a fragment retaining kanji (`食べる` → `食べ`)
- For words with no kanji at all (`する`, `できる`), give up and discard the card

**How today’s questions are chosen**

Sort by the product of `priority weight` × `JLPT level proximity` × `overdue multiplier`.

- Priority: high 1.0 / normal 0.7 / low 0.4
- Overdue multiplier: not overdue 0.8, within 3 days 1.0, over a week 1.5

In use, I noticed tied words were always selected in the same order.

- Multiply the final score by ±15% jitter to randomize ties
- Priority and overdue differences (usually 1.4–3×) exceed the jitter, so urgent cards do not fall behind.
- New cards were biased toward input order, so I created a separate RPC that randomly selects them from the database.

**Automatic mastery / leeches**

- Two consecutive Easy ratings automatically mark a word 「Mastered」 and remove it from the queue
- Frequently missed words are marked as leeches (default 8 misses, configurable)

**Session restoration**

- Users needed to continue after leaving the app mid-quiz
- localStorage stores only word-ID order and current position. Examples and distractors are heavy, so they are regenerated when loading.
- Discard the session when the date changes

**Accuracy is a weighted average**

Count 「how confidently it is known」 rather than a binary correct/incorrect result.

| Again | Hard | Good | Easy | Mastered during session |
| ----- | ---- | ---- | ---- | -------- |
| 0     | 20   | 50   | 80   | 100      |

Settings also control daily goals (20 words by default), JLPT/priority filters, study reminders, and 22 achievements (word count, consecutive study days, total reviews, flawless sessions, and more).

### Introducing React Native and Expo

1. Switched because the web environment’s 1gb memory limit was unsuitable for on-device LLM use
2. RN was suitable for reusing next.js build output
3. Decided to try expo for easier App Store deployment

More precisely, the screens were not rewritten in RN: it was **a shell wrapping the existing Next.js website in a WebView**.
Screens and logic used the existing web output, with bridges only for native needs such as camera, notifications, and on-device LLM inference.

```txt
[ Next.js (WebView) ]  ←→  bridge  ←→  [ Expo Native ]
     화면 · 로직                       카메라 / 알림 / on-device LLM
```

### Freezing this project and moving to Flutter

- Awkward RN usability:
  - Possibly because vibe coding left optimization incomplete, many parts felt oddly sluggish.
  - The extra js -&gt; swift layer made full use of native features difficult.
- Limits on on-device LLM use
  - Many things failed in subtle ways because it was not native. An iphone15pro should have enough memory for gemma4 e4b, yet the app crashed when using e4b.
  - e2b was too small and kept giving strange answers. Prompts over 1,000 characters did not work properly, and function calling was unreliable.
- Expo inconvenience
  - The free plan has build limits =&gt; subscribing to a paid plan felt a bit expensive for a side project.
    - Low build priority could mean waiting an hour before a build started...

For these reasons, I archived the project and switched entirely to Flutter.

I chose flutter for simultaneous ios/android support and its near-native behavior despite being cross-platform.

## Retrospective

**What went well**

- Fast feature development through vibe coding =&gt; replacing OCR, withdrawing guest mode, and moving to RN all happened at a pace that allowed trying first and judging afterwards, without delaying decisions.
- Filling the dictionary with open-source data and LLM translation. Manually entering tens of thousands of words was not feasible for a personal project.
- Getting through App Store review and releasing the app.
  Side projects often stop once they run locally, but the experience of store registration, review, and the deployment pipeline remains.

**What could have gone better**

- **Making an on-device LLM a prerequisite for features.**
  I should have verified the models first and designed the features afterwards, but did the reverse.
  In the end e4b crashed from memory pressure while e2b lacked quality, forcing repeated cuts to completed features to fit model capabilities.
- Withdrawing guest mode only after implementing all of IndexedDB. I had not estimated state-management complexity before starting.
- Allowing some domain logic to spread into Supabase triggers and RPCs.
  Convenient at first, this directly became migration cost when I chose to run the backend myself.
- The cost of vibe coding: the discipline of distinguishing 「it works」 from 「it is verified」 came late.
